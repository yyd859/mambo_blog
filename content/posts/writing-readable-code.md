我们经常说代码要「可读」，但可读性到底是什么？

## 可读性不是注释

很多人把可读性等同于注释的多少。这是个误解。

好的代码应该通过命名、结构、抽象层次来传达意图。注释的作用不是解释「做什么」——好的命名已经做到了——而是解释「为什么」：

```python
# 不好：注释重复了代码做的事
# 遍历用户列表
for user in users:
    send_email(user)

# 好：名字本身就说明了意图
for user in pending_verification_users:
    send_verification_email(user)
```

只有当代码本身无法传达原因时，注释才有价值：

```python
# 这里用 sleep(0.1) 是为了避免触发 API 的速率限制（100 req/s）
# 参考：https://api.example.com/docs/rate-limits
time.sleep(0.1)
```

## 可读性关乎读者，不是作者

写代码的时候我们总是站在作者的角度。但代码被读的次数远多于被写的次数，而且读者经常不是作者自己。

一个有用的启发式方法：**让代码对六个月后的自己可读**。那时你已经忘掉了所有上下文，只剩下代码本身。

## 局部性原则

可读的代码让读者不需要跳来跳去就能理解一段逻辑。这意味着：

1. 相关的代码放在一起
2. 变量的声明和使用的距离尽量短
3. 函数尽量短，做一件事

不是说文件必须短，而是说**读者的视线移动距离要短**。

## 一致性比风格更重要

团队里用 camelCase 还是 snake_case，用 tabs 还是 spaces，这些选择本身没有对错。真正重要的是**全局一致**。

不一致的风格会打断读者的节奏，让大脑不得不分心处理格式问题，而不是专注于逻辑。这就是为什么 linter 和 formatter 如此有价值——它们把风格决策自动化，让所有人专注于更重要的事情。

---

可读性是一种对未来读者（包括未来的自己）的尊重。写代码不只是让机器执行，而是与人沟通。
